# NotBad Privacy Detector Agent — правила разработки

## Обязательные ограничения
- Не создавать git-коммиты без прямого запроса пользователя.
- NotBad Privacy Detector Agent — read-only auditor & detector. Не добавлять автоматическое удаление, очистку Registry, изменение Windows Search, Defender, служб или пользовательских файлов.
- Не отправлять пути, результаты, хеши или содержимое файлов по сети.
- Ошибка одного scanner не должна останавливать аудит; junction/reparse points по умолчанию не обходить.

## Перед каждой сборкой для передачи пользователю
Запустить `.\scripts\verify.ps1`. Скрипт обязан успешно выполнить тесты, single-file publish, startup smoke-test и проверку завершения процесса. Нельзя выдавать EXE, если этап завершился ошибкой.

На Windows `TEMP` и `TMP` направлять в writable-каталог рабочей копии. `PermissionError`, `UnauthorizedAccessException` и mapped-section lock сначала перепроверять вне sandbox; не считать их дефектами кода без повторного запуска.

## Локализация и архитектура
- Английский — обязательный fallback; русский выбирается только для `ru-*` UI-культуры.
- Новые строки добавлять в `LocalizationService`, в XAML использовать `{local:Loc Key}`.
- В русской локализации строго соблюдать дружеский, уважительный тон на «ты» («ты», «твой», «тебе», «выбери», «посмотри»), без канцеляризмов и без формальных «Вы/Вам/Ваш».
- `Core/` не зависит от WPF; каждый источник данных реализует `IPrivacyScanner`; SQLite не хранит содержимое файлов.
- Новая логика сопровождается тестом в `tests/PrivacyAudit.Tests/`.

## Стандарты UI и UX
- Каждая интерактивная кнопка, дропдаун, ползунок и поле ввода обязаны иметь информативную всплывающую подсказку (`ToolTip`), сформулированную простым и понятным языком.
- На каждой ключевой форме/вкладке должна быть кнопка «Легенда и информация» со сворачиваемым блоком справки по всем элементам управления.

## Актуализация документации (Vibecoding / AI-разработка)
- При каждом мажорном изменении, добавлении новых функций, изменении UI-элементов, фильтров, навигации или архитектуры компонентов ОБЯЗАТЕЛЬНО обновлять каноническую низкоуровневую документацию в `docs/`: прежде всего `docs/PROJECT_MAP.md` и `docs/ARCHITECTURE.md`, а также профильные `docs/TESTING.md`, `docs/BUILDING.md` и другие документы по назначению.
- `README.md` и `README.ru.md` — синхронные маркетинговые страницы продукта и важная информация для конечного пользователя. Добавлять туда только крупные пользовательские преимущества и killer features, коротко и в продуктовой стилистике. Не переносить в README перечни кнопок, обработчиков, фильтров, алгоритмов, потоков, схем, порогов и историю реализации.
- Технические и vibecoding/AI-development хинты хранить в низкоуровневых документах внутри `docs/`, явно связывать перекрёстными Markdown-ссылками и не дублировать длинными блоками между файлами.
- Описывать назначение новых возможностей и их взаимодействие с существующими модулями (например, фильтрация, сканирование медиа, UI-компоненты, структура вкладок) в соответствующем документе под `docs/`. README обновлять только если изменение существенно меняет позиционирование или главные возможности продукта.
